Deployment checklist

A grouped pre-deploy checklist covering config, security, database, operations and rollback, with every item linking to the page that explains it.

CurrentUpdated 2026-09-08·Production

Work through this before the first production deploy, and again before any release that changes how the service is exposed, authenticated or stored. Every item is one line and links to the page that explains why it is here — the checklist is an index, not a substitute for the reasoning.

Not every item applies to every service. Deciding an item does not apply is fine; skipping it because you did not read it is not.

#Configuration and secrets

  • [ ] All configuration comes from environment variables, not committed files — Configuration
  • [ ] A single config.js is validated with Zod 4 at boot and exported frozen — Configuration
  • [ ] The process exits non-zero when a required variable is missing, before binding a port — Configuration
  • [ ] No secret has a fallback default anywhere in the codebase — Configuration
  • [ ] process.env is read in exactly one module, enforced by a lint rule — Configuration
  • [ ] No NODE_ENV branch exists in business logic — Configuration
  • [ ] NODE_ENV=production is set in the image; staging uses it too, with a separate APP_ENV label — Dockerfile
  • [ ] .env is in .gitignore and .dockerignore; only .env.example is committed — Running the examples
  • [ ] Secrets are injected from a secret store, not baked into the image or a build arg — Secrets management
  • [ ] No secret appears in docker history, docker inspect, or any image layer — Dockerfile
  • [ ] Every environment has its own credentials; staging cannot reach production data — Secrets management
  • [ ] Secret rotation has been performed once, as a drill, without downtime — Secrets management
  • [ ] The safe (non-secret) config view is logged once at boot with the git SHA — Observability
  • [ ] Feature flags default to off and each has a removal date — Configuration

#HTTP security headers

  • [ ] helmet 8.3.0 is registered before the routes — Security headers with Helmet
  • [ ] A Content-Security-Policy is set and tested, not left at the default for an API that serves HTML — Security headers
  • [ ] HSTS is enabled with a meaningful max-age, after confirming HTTPS works everywhere — HTTPS and TLS
  • [ ] X-Content-Type-Options: nosniff and a frame-ancestors policy are present — Security headers
  • [ ] x-powered-by is disabled — Security headers with Helmet
  • [ ] CORS uses an explicit origin allow-list; no reflected origin, no * with credentials — CORS misconfiguration
  • [ ] app.set('trust proxy', …) matches your actual proxy depth — Request and response

#TLS

  • [ ] TLS terminates at a load balancer or reverse proxy, not in Node — HTTPS and TLS
  • [ ] HTTP redirects to HTTPS, and the app rejects plaintext behind the proxy — HTTPS and TLS
  • [ ] TLS 1.2 minimum; TLS 1.3 preferred; weak ciphers disabled — HTTPS and TLS
  • [ ] Certificate renewal is automated and alerted on at 30 days remaining — HTTPS and TLS
  • [ ] Internal service-to-service traffic is encrypted, or the network is genuinely private — HTTPS and TLS
  • [ ] The database connection uses TLS and verifies the server certificate — PostgreSQL with pg

#Authentication and authorization

  • [ ] Passwords are hashed with argon2 0.45.1 (or bcrypt 6.0.0), never stored or logged — Password hashing
  • [ ] Session cookies are httpOnly, secure, sameSite, and scoped to a path — Cookies
  • [ ] Sessions are stored in Redis, not MemoryStore — Authentication
  • [ ] The session id is regenerated on login and destroyed on logout — Authentication and session security
  • [ ] JWTs specify the algorithm on verification; alg: none and algorithm confusion are impossible — JWT pitfalls
  • [ ] Token expiry is short and there is a working revocation story — JWT pitfalls
  • [ ] Every route that returns or mutates a record checks ownership, not just authentication — IDOR and broken object-level authorization
  • [ ] CSRF protection is in place for cookie-authenticated state changes, using csrf-csrf 4.0.3 or a session-bound double-submit token — CSRF
  • [ ] Login, password reset and token endpoints are rate-limited separately and more strictly — Rate limiting and abuse
  • [ ] Authentication failures are logged without the credential — Logging without leaking PII

#Rate limiting and abuse

  • [ ] express-rate-limit 8.7.0 is configured with rate-limit-redis 6.0.1, not the in-memory store — Rate limiting
  • [ ] The key is a trustworthy client identity, given your proxy configuration — Rate limiting
  • [ ] Health and readiness endpoints are exempt from rate limiting — Health and readiness probes
  • [ ] Expensive endpoints — search, export, upload — have their own tighter limits — Rate limiting and abuse
  • [ ] Request body size is capped on every parser — File uploads
  • [ ] There is a server-level request timeout so a slow client cannot hold a connection — Graceful shutdown

#Input validation

  • [ ] Every request body, query and route parameter is validated with Zod 4 at the edge — Validation
  • [ ] Handlers receive the parsed value, never the raw req.body — Validation
  • [ ] Update and create schemas allow-list fields; no object is spread into a model — Mass assignment
  • [ ] Pagination limits are capped server-side regardless of what the client sends — Performance
  • [ ] Every SQL query is parameterised; scripts/lint-sql.mjs passes — SQL injection
  • [ ] Mongo queries cannot receive an operator object from user input — NoSQL injection
  • [ ] Uploads are checked by magic bytes with file-type 22.0.2, not by extension or content-type — File upload security
  • [ ] Uploads are size-limited, stored outside the web root, and served with a safe content type — File upload security
  • [ ] Any user text rendered into HTML is escaped or sanitized — XSS
  • [ ] File paths built from user input are resolved and confirmed inside the allowed root — Files and paths

#Database

  • [ ] Migrations run as a discrete deploy step, never on application boot — Migrations
  • [ ] Every migration is backward-compatible with the currently running version — Migrations
  • [ ] Every migration has been tested against a production-sized copy — Migrations
  • [ ] Adding a column, an index or a constraint does not take a blocking lock — Migrations
  • [ ] A rollback path exists for every migration, or the change is provably additive — Migration strategy
  • [ ] Indexes exist for every query in the request path; EXPLAIN ANALYZE confirms no sequential scans — Indexing basics
  • [ ] No N+1 query in any list endpoint — N+1 queries
  • [ ] Pool size × replicas × processes is below the database's max_connections, with headroom — Connection pooling
  • [ ] A statement timeout and a pool acquire timeout are set — Retries and timeouts
  • [ ] Transaction boundaries are in the service layer and never span an outbound HTTP call — Transactions
  • [ ] The application's database user has only the privileges it needs — Secrets management

#Backups and restore

  • [ ] Automated backups are enabled with a retention period matching your requirements — Migrations
  • [ ] Point-in-time recovery is enabled where the data justifies it — Choosing a database
  • [ ] A restore has actually been performed into a scratch environment. An untested backup is not a backup — Migrations
  • [ ] Restore time has been measured and is acceptable to the business — Migrations
  • [ ] Backups are stored in a separate account or region from the primary — Secrets management
  • [ ] Backup failures raise an alert; silent backup failure is the default failure mode — Observability

#Graceful shutdown

  • [ ] SIGTERM and SIGINT are handled; the handler is idempotent — Graceful shutdown
  • [ ] Readiness flips to false first, with a drain delay before the socket closes — Graceful shutdown
  • [ ] server.close() is followed by server.closeIdleConnections() — Graceful shutdown
  • [ ] In-flight requests are awaited under a hard deadline, exiting non-zero on timeout — Graceful shutdown
  • [ ] Queue workers stop consuming and finish or return held jobs before pools close — Graceful shutdown
  • [ ] Database and Redis connections close after in-flight work, in dependency order — Graceful shutdown
  • [ ] The total shutdown budget fits inside terminationGracePeriodSeconds — Graceful shutdown
  • [ ] server.keepAliveTimeout exceeds the proxy's idle timeout, with headersTimeout above it — Graceful shutdown
  • [ ] docker stop returns in under a couple of seconds, proving SIGTERM reaches Node — Dockerfile
  • [ ] PID 1 is an init (dumb-init/tini) or node directly — never a shell or npm — Dockerfile
  • [ ] The logger is flushed before process.exit() — Observability

#Health probes

  • [ ] Separate liveness, readiness and startup endpoints exist — Health and readiness probes
  • [ ] Liveness checks nothing external. No database, no cache, no downstream service — Health and readiness probes
  • [ ] Readiness checks only the dependencies a request genuinely cannot be served without — Health and readiness probes
  • [ ] Every dependency check has a timeout, and results are cached for a second or two — Health checks
  • [ ] Probes return 200 or 503 and reveal no hostnames, versions, or error strings — Health and readiness probes
  • [ ] Readiness periodSeconds is small enough for the shutdown flag to be noticed — Graceful shutdown
  • [ ] Probe paths are registered before auth middleware and excluded from access logs — Health and readiness probes
  • [ ] The database-down case has been tested: pods go unready and stay running — Health and readiness probes

#Logging

  • [ ] Structured JSON logs to stdout with pino 10.3.1; no log files inside the container — Logging
  • [ ] Every log line carries a correlation id via AsyncLocalStorage — Observability
  • [ ] The id is accepted from an inbound header and propagated on outbound calls — Observability
  • [ ] Redaction is configured for authorization headers, cookies, passwords and tokens — Logging without leaking PII
  • [ ] No PII, credential or full request body is logged — Logging without leaking PII
  • [ ] Probe endpoints are excluded from access logs — Health and readiness probes
  • [ ] Errors are logged once, at the boundary, with a stack and the correlation id — Error handling
  • [ ] Log level is configurable; debug is off in production — Configuration
  • [ ] Stack traces and internal error details never reach the client — Error handling
  • [ ] pino-pretty is a devDependency and is not used in production — Logging

#Monitoring and alerting

  • [ ] Request rate, error rate and latency percentiles are recorded per route pattern — Observability
  • [ ] Metric labels use route patterns, never ids or raw paths — Observability
  • [ ] Event-loop delay is measured with perf_hooks.monitorEventLoopDelay — Observability
  • [ ] Connection-pool in-use and waiting counts are exported — Connection pooling
  • [ ] Outbound dependency latency and error rate are recorded per dependency — Observability
  • [ ] Queue depth and oldest-job age are monitored — Observability
  • [ ] At least one business metric is monitored — orders, signups, payments — Observability
  • [ ] Alerts fire on symptoms (error rate, latency, business volume), not causes (CPU, memory) — Observability
  • [ ] Every alert has a runbook link and a named owner — Observability
  • [ ] An SLO and error budget exist for the most important endpoint — Observability
  • [ ] Tracing is enabled and sampled, with the trace id in log lines — Observability
  • [ ] /metrics is not publicly reachable — Observability
  • [ ] Someone is actually on call, and the paging path has been tested — Observability

#Dependencies and supply chain

  • [ ] npm ci is used everywhere; package-lock.json is committed — Continuous integration
  • [ ] npm audit --omit=dev --audit-level=high passes in CI — Dependency auditing
  • [ ] No deprecated package is in use: multer@1.x, csurf, request, or an Express 4 async wrapper — Dependency auditing
  • [ ] prom-client has been replaced by @prometheus-io/client if metrics are exported — Observability
  • [ ] Node 24 LTS is the runtime; nothing is on an EOL line — Prerequisites
  • [ ] The container image is scanned, and the base image is pinned and rebuilt on a schedule — Dockerfile
  • [ ] GitHub Actions are pinned to a major, or a SHA where they touch secrets — Continuous integration
  • [ ] An automated dependency-update bot is enabled — Dependency auditing

#Container and resources

  • [ ] Multi-stage build; npm ci --omit=dev in the runtime stage — Dockerfile
  • [ ] .dockerignore excludes .env, .git and node_modules — Dockerfile
  • [ ] The container runs as the non-root node user, enforced by runAsNonRoot — Dockerfile
  • [ ] Capabilities are dropped and the root filesystem is read-only where possible — Dockerfile
  • [ ] Memory and CPU requests and limits are set on every container — Dockerfile
  • [ ] --max-old-space-size is set relative to the container memory limit — Performance
  • [ ] One Node process per container; scaling is by replicas — Clustering
  • [ ] If clustering is used, availableParallelism() is used, not os.cpus().length — Clustering
  • [ ] The image was built for the deployment architecture — Dockerfile
  • [ ] At least two replicas run, across failure domains — Clustering

#Performance

  • [ ] The service has been load-tested against a realistic dataset — Performance
  • [ ] A latency SLO exists and current p99 meets it — Performance
  • [ ] No synchronous fs, zlib or crypto call is on the request path — Performance
  • [ ] Outbound HTTP uses a shared, pooled agent with keep-alive and timeouts — Performance
  • [ ] Compression happens at the proxy, or in Node — never both — Compression
  • [ ] Every list endpoint paginates with a server-enforced maximum — Performance
  • [ ] The database slow-query log is enabled and has been reviewed — Indexing basics

#Deploy and rollback

  • [ ] One image is built once and promoted through environments unchanged — Continuous integration
  • [ ] Images are tagged with the git SHA, not only latest — Dockerfile
  • [ ] Deployment is rolling or blue/green, with health gating and no downtime — Health and readiness probes
  • [ ] The built image was booted and smoke-tested in CI before being pushed — Continuous integration
  • [ ] The rollback procedure has been executed at least once, not just written down — Continuous integration
  • [ ] Rollback does not require reversing a migration; schema changes are backward-compatible — Migration strategy
  • [ ] Old and new versions can run simultaneously during a rolling deploy — Migrations
  • [ ] Config changes are deployable and revertible independently of code — Configuration
  • [ ] There is a documented incident path: who is paged, who declares, who communicates — Observability
  • [ ] The first deploy is scheduled when the people who wrote it are awake — Continuous integration

#Production considerations

Two things about the checklist itself.

Rerun it on a schedule. A service that passed in March fails in September: a dependency was deprecated, an index was outgrown, a certificate is close to expiry, max_connections was reached by a new replica count. Quarterly is a reasonable cadence; after any incident is mandatory.

Treat unchecked boxes as a written-down risk, not a blocker. Very few teams check every box before the first deploy. What separates a good outcome from a bad one is knowing which boxes are unchecked and having decided that consciously. The dangerous state is not "we have no rollback plan" — it is "we assumed we had one".

Three items are worth more than the rest combined, because each one converts a routine problem into an outage:

  1. The restore has been tested. An untested backup is a belief, not a capability.
  2. The rollback has been executed. A procedure nobody has run does not work; you find out during the incident.
  3. Liveness checks nothing external. This is the item that can take down an entire healthy fleet because of someone else's five-second blip.

#Common mistakes

  • Treating the checklist as a formality. Ticking a box you did not verify is worse than an empty box, because it stops anyone looking again.
  • Assuming backups work. Automated backups fail silently for months. Restore, or you do not have backups.
  • Writing a rollback plan without running it. The first execution should not be during an incident.
  • A liveness probe that checks the database. One database blip restarts every pod at once.
  • Migrations on application boot. N replicas start; N migrations race.
  • A migration that is not backward-compatible. During a rolling deploy both versions are live; a dropped column breaks the old one instantly.
  • Deploying on a Friday afternoon, or when the author is unreachable.
  • Checking the security boxes only before launch. Every release changes the attack surface.
  • Ignoring a box because "it does not apply". Write down why. Half the time the reason does not survive being written.
  • No staging environment that resembles production. Everything here passes on a laptop with one user and an empty database.
  • Sizing the connection pool per process and forgetting the replica count. Multiply, then compare to max_connections.
  • Shipping with debug logging on. Cost, noise, and the most likely path to logging something you should not.
