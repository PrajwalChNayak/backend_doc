What this covers

A map of the nine sections with a reason to read each, and an explicit list of what this handbook deliberately leaves out.

CurrentUpdated 2026-09-08·Getting Started

Nine sections, roughly a hundred pages, all written against Node 24 LTS and Express 5. This page tells you what is in each one and — just as importantly — what is not here at all, so you do not spend an hour searching for a topic that was never written.

#The nine sections

SectionRead it when
Getting StartedYou want the scope, the opinions, the tooling and how to run the code.
Node.js FundamentalsYou need to understand the runtime under Express before you can debug it.
Express FundamentalsYou are writing routes, middleware and error handling, or laying an app out.
Express LibrariesYou need to pick and configure the packages a real API depends on.
DatabasesYou are talking to a database directly — drivers, pools, transactions, migrations.
ORMs and Query BuildersYou are deciding whether to use an ORM, or already have one and want it safe.
SecurityAnything you build is reachable from the internet.
ProductionYou need it deployed, observable, and able to survive a restart.
ReferenceYou are looking something up rather than learning it.

#Getting Started

Four pages. Introduction states the scope and the opinions. This page maps the site. Prerequisites covers Node 24, version managers, npm 11, Docker, and editor setup. Running the examples covers the examples/ directory and the site's own validators.

#Node.js Fundamentals

The runtime itself, because most Express problems are actually Node problems.

  • Runtime and the event loop — why one blocking call stalls every concurrent request.
  • ESM vs CommonJS — the interop rules, and why the site is ESM-only.
  • package.json and npm scripts — fields that matter, and node --run.
  • Async/await and promises — concurrency, Promise.all vs allSettled, cancellation.
  • Error handling — operational vs programmer errors, and when to let the process die.
  • Streams and buffers — how to move data without loading it into memory.
  • Files and paths — node:fs/promises, and path traversal.
  • The http module — what Express is a thin layer over.
  • Environment variables and config — --env-file and the shape of config.
  • The built-in test runner — node --test, no test framework required.
  • Debugging — the inspector, heap and CPU profiles.
  • Native TypeScript support — type stripping, and exactly what it will not do.

#Express Fundamentals

Express 5 from the ground up.

  • Setup and project structure — a layout that survives growth.
  • Routing — first match wins, in registration order.
  • Route parameters and path syntax — what path-to-regexp v8 accepts, and what it now rejects.
  • Middleware — the stack, and ordering rules that decide correctness.
  • Request and response — the objects every handler gets, with the Express 5 changes.
  • Error handling — where a rejected async handler ends up.
  • Routers and modularity — splitting the app up.
  • Static files — including the dotfiles default that breaks /.well-known.
  • Templating — server-rendered views, and escaping.
  • Layered architecture — route, controller, service, repository.

#Express Libraries

The packages you actually install, each with the current major version and its failure modes.

  • Security headers with Helmet — what each header buys you.
  • CORS — the preflight, and why origin: true is not "allow all".
  • Rate limiting — and why an in-memory store breaks across replicas.
  • Validation — Zod 4 at the edge.
  • Authentication — sessions vs tokens, honestly compared.
  • Password hashing — argon2 parameters that mean something.
  • File uploads — multer 2.x, since 1.x is deprecated.
  • Logging — pino, structured output, redaction.
  • Compression — and when to leave it to the proxy.
  • Cookies — the attribute matrix that decides whether they are safe.
  • API documentation — OpenAPI generated from the schemas you already wrote.
  • Testing — node:test plus supertest.
  • Process management — supervisors, restarts, signals.

#Databases

  • Choosing a database — a decision list with the costs attached.
  • PostgreSQL with pg, MySQL with mysql2, SQLite, MongoDB, Redis — the drivers, parameterised.
  • Connection pooling — the setting that most often causes a production outage.
  • Transactions — isolation levels and where to put the boundary.
  • Migrations and Seeding — schema change without downtime.
  • Health checks — a query cheap enough to run every few seconds.
  • Retries and timeouts — because the network is not reliable.
  • N+1 queries and Indexing basics — where your latency actually goes.

#What this does NOT cover

Scope is a feature. These are deliberate omissions, not gaps waiting to be filled.

Not coveredWhy, and where to go instead
GraphQLA different request model, a different security model (query depth and complexity limits, persisted queries, per-field authorization) and a different tooling stack. Covering it properly would be its own handbook; covering it briefly would be worse than not covering it.
gRPC and Protocol BuffersSame reason. It is a good choice for service-to-service traffic, and nothing here applies to it beyond the process-level operational pages.
WebSockets and realtimeMentioned where it changes an operational decision — graceful shutdown has to drain long-lived connections, and clustering breaks broadcast without a shared backplane — but there is no page on ws, Socket.IO, presence, or scaling fan-out.
Frontend frameworksOut of scope for this pass. A Next.js section is planned as a later addition and will cover the client, rendering, and the boundary with these APIs. React, Vue and Svelte specifics stay out.
Kubernetes operationsThe pages tell you what your application must do to behave in an orchestrator — SIGTERM handling, probe endpoints, the deregistration race, one process per container. Writing manifests, Helm charts, ingress, service meshes, autoscaling and cluster operations are not covered.
Message brokers in depthQueues appear where they affect shutdown ordering and background work, and BullMQ is named. RabbitMQ topologies, Kafka partitioning and consumer-group semantics, exactly-once delivery and event-driven architecture are not covered.

Also out of scope: serverless platform specifics beyond the connection-pooling consequence, mobile clients, browser JavaScript, CSS, machine learning, and any cloud provider's console.

Note

"Not covered" means the site will not teach it. It does not mean avoid it. If your problem genuinely needs a message broker, use one — just get the design from a source that specializes in it.

#How to tell whether a page is current

Every page carries status and updated in its front matter. status: current is the default and the vast majority. status: legacy means the page documents old-Node or Express 4 material on purpose; there is exactly one such page. status: deprecated marks material kept only so search finds it and tells you what replaced it.

Inline, Express 4 idioms are wrapped in a :::legacy callout and removed APIs in a :::deprecated callout. If you see neither marker, the code is meant for Express 5 on Node 24.

#Common mistakes

  • Searching for a topic in the wrong section. Rate limiting has a configuration page under Express Libraries and a threat page under Security. Same for logging, CORS, file uploads and security headers — the library page tells you how, the security page tells you why and what breaks.
  • Assuming an omission is an oversight. The table above is the complete out-of-scope list. GraphQL is not hiding in a subsection.
  • Reading Production before Security. Most of the checklist items in Deployment checklist link into Security. The checklist is an index, not a substitute.
  • Expecting Express 4 answers. Only Express 4 → 5 migration contains them. Everywhere else, an Express 4 snippet found on the web will contradict this site — and the site is the one written against 5.2.1.
