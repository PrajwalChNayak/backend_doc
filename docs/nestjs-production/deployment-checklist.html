Deployment checklist

A grouped pre-deploy checklist for a NestJS 12 service — config, validation, security, database, shutdown, probes, observability, dependencies, resources and rollback.

CurrentUpdated 2026-09-11·NestJS Production

Work through this before the first production deploy of a Nest service, and again before any release that changes how it is exposed, authenticated or stored. Every item is one line and links to the page that explains why it is there — the checklist is an index, not a substitute for the reasoning.

Not every item applies to every service. Deciding one does not apply is fine; skipping it because you did not read it is not.

#Build and artifact

  • [ ] The build runs nest build against tsconfig.build.json, and the entry point is dist/main.js — Build and deployment
  • [ ] Every non-TypeScript asset is listed under compilerOptions.assets in nest-cli.json — Build and deployment
  • [ ] includeLibraryAssets is set if a monorepo library ships assets — Monorepo and library mode
  • [ ] The container command is node dist/main.js — never nest start, npm run, or a shell form — Docker
  • [ ] @nestjs/cli, @nestjs/schematics, typescript and the test runner are devDependencies and are absent from the runtime image — Build and deployment
  • [ ] reflect-metadata, rxjs and anything a global pipe needs are in dependencies, not devDependencies — Docker
  • [ ] package.json is copied into the runtime image, so "type" and imports still apply — Docker
  • [ ] The module format is decided repository-wide, with moduleResolution: "nodenext" if it is ESM — ESM vs CommonJS in production
  • [ ] Source maps are emitted and --enable-source-maps is passed, or maps are uploaded to the error tracker — Build and deployment
  • [ ] One image is built once, tagged with the git SHA, and promoted unchanged through environments — Build and deployment

#Configuration and secrets

  • [ ] All configuration comes from the environment; nothing environment-specific is baked into the image — Environment configuration
  • [ ] ConfigModule.forRoot validates a Standard Schema (Zod 4) at boot and the process exits non-zero on failure — Configuration
  • [ ] No secret has a default anywhere: getOrThrow, never get(key, fallback) — Environment configuration
  • [ ] There is no retry loop around configuration; the crash loop is what halts the rollout — Environment configuration
  • [ ] process.env is read only inside the config layer, enforced by a lint rule — Environment configuration
  • [ ] No NODE_ENV branch exists in a provider or a service — Environment configuration
  • [ ] NODE_ENV=production is set in the image; staging uses it too, with a separate APP_ENV label — Docker
  • [ ] ignoreEnvFile is on in production so a stray .env cannot shadow injected variables — Environment configuration
  • [ ] .env is in .gitignore and .dockerignore; only .env.example is committed — Docker
  • [ ] Secrets are injected from a secret store, never from a build arg or an image layer — Secrets and config validation
  • [ ] No secret appears in docker history, docker inspect, or any layer — Docker
  • [ ] Every environment has its own credentials; staging cannot reach production data — Secrets management
  • [ ] Secret rotation has been performed once, as a drill, without downtime — Secrets management
  • [ ] The safe (allow-listed) config view is logged once at boot with the git SHA — Environment configuration
  • [ ] Adding a required variable was done in three deploys: optional, set everywhere, then required — Environment configuration

#Validation and serialization

  • [ ] A ValidationPipe is registered globally with whitelist: true and transform: true — The ValidationPipe
  • [ ] forbidNonWhitelisted is on, or unknown properties are knowingly stripped rather than passed through — Whitelisting and unknown properties
  • [ ] The same global pipe is registered in the e2e test setup, so tests exercise the real pipeline — End-to-end tests
  • [ ] Every body, query and route parameter has a DTO or a schema; no handler reads a raw request — DTOs
  • [ ] Create and update DTOs allow-list fields; no client object is spread into an entity — Validation as a security control
  • [ ] Pagination limits are capped server-side regardless of what the client sends — Performance
  • [ ] Responses go through a serializer that strips internal fields, and it is not applied to huge lists by default — Serialization
  • [ ] Request body size is capped at the parser, and upload size is capped separately — File uploads
  • [ ] Uploads are checked by magic bytes, not by extension or content-type — File upload security
  • [ ] Route paths use path-to-regexp 8 syntax; no Express 4 wildcard or optional-parameter forms remain — Routing and path syntax

#HTTP security

  • [ ] helmet 8.3.0 is registered before the routes — Security headers
  • [ ] A Content-Security-Policy is set deliberately, not left at a default an API does not need — Security headers
  • [ ] HSTS is enabled with a meaningful max-age, after confirming HTTPS works everywhere — Security headers
  • [ ] x-powered-by is disabled on the underlying Express instance — Security headers
  • [ ] CORS uses an explicit origin allow-list; no reflected origin and no * with credentials — CORS
  • [ ] trust proxy matches your actual proxy depth, so client IPs and rate-limit keys are real — How Nest uses Express
  • [ ] TLS terminates at a load balancer or proxy, not in Node — HTTPS and TLS
  • [ ] The database connection uses TLS and verifies the server certificate — PostgreSQL

#Authentication and authorization

  • [ ] Passwords are hashed with argon2 0.45.1 or bcrypt 6.0.0, never stored or logged — Authentication
  • [ ] A global authentication guard is registered, with an explicit @Public() escape hatch — Guards
  • [ ] JWT verification pins the algorithm; alg: none and algorithm confusion are impossible — JWT pitfalls
  • [ ] Token expiry is short and there is a working revocation story — JWT pitfalls
  • [ ] Session cookies are httpOnly, secure, sameSite, and the session id is regenerated on login — Authentication and session security
  • [ ] Every route that returns or mutates a record checks ownership, not just authentication — Authorization and IDOR
  • [ ] Authorization is enforced in a guard or the service, never only in the client — Authorization
  • [ ] CSRF protection is in place for cookie-authenticated state changes — CSRF
  • [ ] Authentication failures are logged without the credential — Safe logging

#Rate limiting and abuse

  • [ ] @nestjs/throttler 6.5.0 is configured with a shared Redis storage, not the in-process default — Rate limiting with Throttler
  • [ ] The throttler key is a trustworthy client identity given your proxy configuration — Rate limiting and abuse
  • [ ] Login, password reset and token endpoints have their own stricter limits — Rate limiting and abuse
  • [ ] Health and readiness endpoints are exempt from throttling — Health and readiness probes
  • [ ] Expensive endpoints — search, export, upload — have their own tighter limits — Rate limiting and abuse
  • [ ] A server-level request timeout stops a slow client holding a connection through your drain window — Graceful shutdown

#Database

  • [ ] Migrations run as a discrete deploy step, never from main.ts or an onModuleInit hook — Migrations
  • [ ] Every migration is backward-compatible with the version currently serving traffic — Migrations
  • [ ] synchronize is off in every environment that holds data you care about — TypeORM
  • [ ] Every migration has been tested against a production-sized copy — Migrations
  • [ ] Adding a column, index or constraint does not take a blocking lock — Migrations
  • [ ] Indexes exist for every query on the request path; EXPLAIN ANALYZE shows no sequential scans — Indexing basics
  • [ ] No N+1 query in any list endpoint — Avoiding N+1
  • [ ] Pool size × processes × replicas is below max_connections, with headroom — Connection pooling
  • [ ] A statement timeout and a pool acquire timeout are set — Retries and timeouts
  • [ ] Transaction boundaries live in the service layer and never span an outbound HTTP call — Transactions
  • [ ] Every query is parameterised; no user input reaches a raw query by interpolation — SQL injection
  • [ ] Mongo queries cannot receive an operator object from user input — NoSQL injection
  • [ ] The application's database user has only the privileges it needs — Secrets management

#Backups and restore

  • [ ] Automated backups are enabled with a retention period matching your requirements — Migrations
  • [ ] Point-in-time recovery is enabled where the data justifies it — Migrations
  • [ ] A restore has actually been performed into a scratch environment. An untested backup is not a backup — Migrations
  • [ ] Restore time has been measured and is acceptable to the business — Migrations
  • [ ] Backups are stored in a separate account or region from the primary — Secrets management
  • [ ] Backup failure raises an alert; silent failure is the default failure mode — Observability

#Graceful shutdown

  • [ ] app.enableShutdownHooks() is called — without it every hook you wrote is dead code — Graceful shutdown
  • [ ] Readiness fails before anything closes, with a drain delay for the load balancer to converge — Graceful shutdown
  • [ ] gracefulShutdownTimeoutMs is set on TerminusModule, or an equivalent delay is implemented — Health checks with Terminus
  • [ ] Queue workers stop consuming in onModuleDestroy and drain in beforeApplicationShutdown — Background jobs with BullMQ
  • [ ] Pools, Redis and external clients close in onApplicationShutdown — never in onModuleDestroy — Graceful shutdown
  • [ ] Every hook is idempotent and catches its own errors, given the v12 hierarchy-level ordering — Graceful shutdown
  • [ ] No code relies on hook ordering between providers within one hook — NestJS 11 → 12 migration
  • [ ] forceCloseConnections: true is set, so idle keep-alive sockets cannot hold app.close() open — Graceful shutdown
  • [ ] server.keepAliveTimeout exceeds the proxy's idle timeout, with headersTimeout above it — Graceful shutdown
  • [ ] The total shutdown budget fits inside terminationGracePeriodSeconds — Graceful shutdown
  • [ ] PID 1 is an init or node directly — never a shell, npm, or the Nest CLI — Docker
  • [ ] docker stop returns in about a second, proving SIGTERM reaches Nest — Docker
  • [ ] An e2e test calls app.close() in afterAll, so a throwing hook fails in CI — Continuous integration
  • [ ] The logger is flushed in onApplicationShutdown — Observability

#Health probes

  • [ ] Separate liveness and readiness endpoints exist, wired to separate probes — Health and readiness probes
  • [ ] Liveness checks nothing external. No database, no cache, no downstream service — Health checks
  • [ ] Readiness checks only the dependencies a request genuinely cannot be served without — Health checks
  • [ ] An impaired-but-serving dependency reports degraded, not down — Health checks with Terminus
  • [ ] Every network indicator has withTimeout, and expensive ones have cacheFor — Health checks with Terminus
  • [ ] A startup probe covers the full NestFactory.create() boot window — Health and readiness probes
  • [ ] livenessProbe.failureThreshold is at least 3; readinessProbe.periodSeconds is small — Health and readiness probes
  • [ ] Probes are @Public(), exempt from throttling, excluded from setGlobalPrefix, and version-neutral — Health and readiness probes
  • [ ] No global filter or interceptor turns a probe's 503 into a 200 — Health and readiness probes
  • [ ] Probe bodies reveal no hostnames, driver errors, versions or connection strings — Health checks with Terminus
  • [ ] The database-down case has been tested: pods go unready and stay running — Health and readiness probes

#Logging

  • [ ] Structured JSON to stdout; no log files inside the container — Logging
  • [ ] bufferLogs: true and app.useLogger() are set, so bootstrap lines share the format — Observability
  • [ ] Every line carries a correlation id from AsyncLocalStorage, not a request-scoped provider — Observability
  • [ ] The id is accepted from an inbound header and propagated on outbound calls — Observability
  • [ ] Background work — crons, queue consumers — opens its own context with a job id — Observability
  • [ ] Redaction is configured for authorization headers, cookies, passwords and tokens — Safe logging
  • [ ] No DTO or request body is logged wholesale — Safe logging
  • [ ] Failures are logged once, in the exception filter, with a stack and the correlation id — Exception filters
  • [ ] Probe endpoints are excluded from access logs — Observability
  • [ ] Stack traces and internal error details never reach the client — Exception filters
  • [ ] Log level is configurable and debug is off in production — Environment configuration
  • [ ] pino-pretty is a devDependency and is not used in production — Logging

#Monitoring and alerting

  • [ ] Request rate, error rate and latency percentiles are recorded per route pattern — Observability
  • [ ] Metric labels are bounded; no ids or resolved paths — Observability
  • [ ] Event-loop delay is measured with perf_hooks.monitorEventLoopDelay — Performance
  • [ ] Connection-pool in-use and waiting counts are exported — Connection pooling
  • [ ] Outbound dependency latency and error rate are recorded per dependency — Observability
  • [ ] Queue depth and oldest-job age are monitored — Background jobs with BullMQ
  • [ ] At least one business metric is monitored — orders, signups, payments — Observability
  • [ ] Tracing is enabled and sampled, with the SDK loaded via --import before the app — Observability
  • [ ] The trace id appears in log lines, so a slow trace links to its logs — Observability
  • [ ] Alerts fire on symptoms (error rate, latency, business volume), not causes (CPU, memory) — Observability
  • [ ] Every alert has a runbook link and a named owner — Observability
  • [ ] /metrics is not publicly reachable — Observability
  • [ ] Someone is actually on call, and the paging path has been tested — Observability

#Dependencies and supply chain

  • [ ] npm ci is used everywhere and package-lock.json is committed — Continuous integration
  • [ ] npm audit --omit=dev --audit-level=high passes in CI — Dependency auditing
  • [ ] Nest packages are on the 12 line where a 12 line exists; @nestjs/throttler is 6.5.0 and @nestjs/graphql is 14.0.0 — NestJS 11 → 12 migration
  • [ ] No deprecated or moved package is in use — multer@1.x is end of life, csurf is archived, and the unscoped NATS client was replaced by @nats-io/transport-node — Dependency auditing
  • [ ] @nestjs/observe is treated as pre-1.0 (0.1.8) if it is used at all — Observability with @nestjs/observe
  • [ ] Node 24 LTS is the runtime; the CI runner also satisfies the CLI's higher floor — Continuous integration
  • [ ] The container image is scanned, and the base image is pinned and rebuilt on a schedule — Docker
  • [ ] GitHub Actions are pinned to a major, or a SHA where they touch secrets — Continuous integration
  • [ ] An automated dependency-update bot is enabled — Dependency auditing

#Container and resources

  • [ ] Multi-stage build; npm ci --omit=dev produces the runtime node_modules — Docker
  • [ ] .dockerignore excludes .env, .git, node_modules and dist — Docker
  • [ ] The container runs as the non-root node user, enforced by runAsNonRoot at the platform — Docker
  • [ ] Capabilities are dropped and the root filesystem is read-only where possible — Docker
  • [ ] Memory and CPU requests and limits are set on every container — Docker
  • [ ] --max-old-space-size is roughly 75% of the container memory limit — Performance
  • [ ] One Nest process per container; scaling is by replicas — Clustering
  • [ ] If clustering is used, availableParallelism() is used and pool sizes are divided by the worker count — Clustering
  • [ ] Every @Cron and @Interval runs exactly once across all workers and replicas — Scheduling
  • [ ] Caches, sessions, rate-limit counters and WebSocket broadcasts use a shared store — Clustering
  • [ ] The image was built for the deployment architecture — Docker
  • [ ] At least two replicas run, across failure domains — Clustering

#Performance

  • [ ] The service has been load-tested against a realistic dataset, profiling dist/, not the watch server — Performance
  • [ ] A latency SLO exists and the current p99 meets it — Performance
  • [ ] grep -r "Scope.REQUEST" src/ has been reviewed; no scope has bubbled up unintentionally — Injection scopes
  • [ ] ClassSerializerInterceptor is not applied globally to endpoints returning large arrays — Serialization
  • [ ] No synchronous fs, zlib or crypto call is on the request path — Performance
  • [ ] Long-running work returns a job id instead of holding the connection — Background jobs with BullMQ
  • [ ] Outbound HTTP uses a shared, pooled agent with keep-alive and timeouts — Performance
  • [ ] No cached response can be served to a different user than it was built for — Caching
  • [ ] The database slow-query log is enabled and has been reviewed — Indexing basics

#Deploy and rollback

  • [ ] CI runs lint, tsc --noEmit, nest build, unit tests and e2e tests against a real database — Continuous integration
  • [ ] CI boots the built artifact and hits /livez before the image is pushed — Continuous integration
  • [ ] Deployment is rolling or blue/green, gated on the readiness probe — Health and readiness probes
  • [ ] The rollback procedure has been executed at least once, not just written down — Build and deployment
  • [ ] Rollback does not require reversing a migration; schema changes are backward-compatible — Migrations
  • [ ] Old and new versions can run simultaneously during a rolling deploy — Migrations
  • [ ] Config changes are deployable and revertible independently of code — Environment configuration
  • [ ] There is a documented incident path: who is paged, who declares, who communicates — Observability
  • [ ] The first deploy is scheduled when the people who wrote it are awake — Continuous integration

#The five that matter most

Most teams do not check every box before the first deploy, and that is survivable. What separates a good outcome from a bad one is knowing which boxes are unchecked and having decided that consciously. The dangerous state is not "we have no rollback plan" — it is "we assumed we had one".

These five each convert a routine problem into an outage:

  1. Liveness checks nothing external. One database blip otherwise restarts every replica simultaneously, and a 60-second failover becomes a 20-minute outage.
  2. enableShutdownHooks() is called and PID 1 is right. Without both, every hook on the previous list is dead code and every deploy drops requests.
  3. Pools close in onApplicationShutdown, not onModuleDestroy. The tidier-looking hook runs while requests are still executing.
  4. The restore has been tested. An untested backup is a belief, not a capability.
  5. The rollback has been executed. A procedure nobody has run does not work, and you find out during the incident.

Rerun the whole list on a schedule. A service that passed in March fails in September: a package was deprecated, an index was outgrown, a new replica count crossed max_connections, a certificate is close to expiry. Quarterly is a reasonable cadence; after any incident is mandatory.

#Common mistakes

  • Ticking a box you did not verify. Worse than an empty box, because it stops anyone looking again.
  • Assuming backups work. Automated backups fail silently for months. Restore, or you do not have backups.
  • Writing a rollback plan without running it. The first execution should not be during an incident.
  • A database check in the liveness probe. The most expensive single mistake on this list.
  • Never calling enableShutdownHooks(). Every termination hook in the codebase is decorative.
  • Closing a pool in onModuleDestroy. In-flight requests turn into 500s on every deploy.
  • Relying on hook ordering across providers after the v12 change. It now runs by hierarchy level.
  • Running migrations at application boot. N replicas start; N migrations race.
  • A migration that is not backward-compatible. During a rolling deploy both versions are live; a dropped column breaks the old one instantly.
  • Registering global pipes and guards in main.ts but not in the e2e setup. The suite tests a pipeline production does not have.
  • @Cron in the web process. It fires once per worker and once per replica.
  • The default throttler or cache store behind multiple processes. Limits multiply and hit rates collapse.
  • Shipping @nestjs/cli and typescript in the runtime image. Size, CVE surface, and a compiler for anyone who gets a shell.
  • Checking the security boxes only before launch. Every release changes the attack surface.
  • Ignoring an item because "it does not apply". Write down why. Half the time the reason does not survive being written.
  • No staging environment that resembles production. Everything here passes on a laptop with one user and an empty database.
